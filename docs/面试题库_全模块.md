## 一、总体架构与技术选型（12 问）

**1.1 一句话讲清整体架构？**
四进程 + 四存储。进程：C++ `api_server`（:8080，控制面：编排/工具/会话/SSE/托管前端/鉴权限流）、Python `llm_gateway`（:8000，OpenAI 兼容网关→DeepSeek，无 key 回退确定性 stub）、Python `retrieval_service`（:8001，检索：结构化过滤下推 + BM25 + pgvector 向量 RRF，HTTP/gRPC 双协议）、Python `ranking_service`（:8002，LightGBM 学习式排序，无模型回退规则分）。存储：PostgreSQL `groupbuy` 库（商品/商户/知识三表 + 向量列）、SQLite `sessions.db`（会话/轮次/反馈/用户画像）、SQLite `observability.db`（推荐审计/LLM 调用审计）、SQLite `ranking_features.db`（排序特征）。

**1.2 为什么控制面用 C++、数据面用 Python？**
控制面是 IO 密集型编排（等 LLM、等检索），C++ 协程用极低资源撑高并发连接，也是我的技术优势栈；LLM 聚合、检索排序这类"数据重、算法迭代快"的逻辑用 Python，改 BM25/换模型不需要重编译。这条"控制面/数据面分离"原则也让商品量从 420 扩到 5320、召回从子串升级到 BM25+向量，C++ 侧一行代码没动。

**1.3 一次 `/v1/chat` 请求的完整链路？**
路由 → 外层 ChatStream 壳（计时开始）→ 内层：加载/创建会话 → SafetyGuard 输入拦截（命中则 BLOCKED 短路）→ 取最近 10 轮历史 + 当前槽位 → TaskPlanner 调 LLM 出 JSON 计划 → 按 action 分支：clarify 直接追问 / respond 直接应答 / retrieve 则顺序执行工具（deal_retriever、deal_ranker、kb_search）→ grounding 组装 → ResponseComposer 生成回复（LLM 或模板）→ 输出脱敏 → 写轮次 → 外层壳统一写 recommendation_logs + llm_calls 两行审计 → 返回。

**1.4 降级链全景——每一层挂了怎么办？**
五级兜底，任何一层失效链路不断：① 网关挂/无 key → C++ 内置确定性 stub（三分支规划）；② 检索服务挂或 `RETRIEVAL_SERVICE_URL` 为空 → DealCatalog 本地子串匹配，且不注册 kb_search；③ PG 挂 → 检索服务降级 json 文件后端；④ `CATALOG_BACKEND=postgres` 但 PG 不可达 → DealCatalog 回退 JSON 文件 → 内置 8 条兜底数据集；⑤ LLM compose 失败/输出不可解析 → 确定性模板回复。改任何一层都不许破坏降级链，这是项目的头号工程纪律。

**1.5 三存储为什么这么拆？**
按访问模式和一致性需求拆：商品/知识是读多写少、需要结构化过滤索引和向量扩展，进 PostgreSQL；会话/轮次/反馈有外键关系（feedback、turns 都 FK 到 sessions 且 CASCADE），必须同库，SQLite WAL 一写多读足够；观测审计写入频率最高、无外键需求，独立 observability.db 避免与会话读写竞争，还能单独备份清理。需要跨库 join（反馈满意率）时用 SQLite ATTACH。

**1.6 为什么用 SQLite 而不是直接上 Redis/PG？**
按当前规模选型、按目标形态设计：单机可演示形态下 SQLite 零部署、WAL 支持一写多读，会话和审计完全够用；但 sessions/feedback 的表结构有意对齐了正式 DDL 风格（主键、外键、索引齐全），迁移时只需换连接层。README 路线图 2.3 里"三库迁 PG"已是明确的后续项——检索库已经先迁了。

**1.7 什么是"契约稳定面"？**
retrieval_service 的三个端点（`/v1/health`、`/v1/retrieve/deals`、`/v1/retrieve/kb`）的 JSON 形状是 C++↔Python 的唯一边界。只要契约不变，Python 侧随便怎么升级（文件后端→PG→加向量通道），C++ 零改动——2.3 路线图就是这么做到"端点契约不变、C++ 侧零改动"的。改响应形状 = 改 C++，所以契约是变更冻结区。

**1.8 为什么服务间用 HTTP JSON 而不是 gRPC？**
Phase 0 的取舍：`proto/agent_service.proto` 已定义但故意不接线。HTTP JSON 调试成本低（curl 可测、明文可查）、两个 Python 服务都是 stdlib 起服务，先把闭环跑通；性能上内部调用不是瓶颈（LLM 延迟占 95%+）。gRPC 迁移列在路线图 2.4，契约已经有 proto 文件兜底。

**1.9 编排器为什么是无状态的，这对扩展意味着什么？**
编排器不持有任何会话状态——会话在 SQLite、商品在 PG/JSON、审计在观测库，每次请求都是"读状态→处理→写回"。所以 QPS 上来时编排层可以直接水平扩展多实例，瓶颈只在存储层：会话热数据迁 Redis、商品库已经在 PG。无状态是有意设计，不是巧合。

**1.10 配置管理的约定和坑？**
全部走环境变量 + `.env`/`.env.local` 文件，`.env.local` 存凭证且 gitignore。加载是 `os.environ.setdefault` 语义且 `.env` 先于 `.env.local` 加载——**先到先得，同名键 .env 赢**，所以每个键只在一个文件里定义（真实环境变量永远最高优先）。这个语义和注释里写的直觉相反，是实测踩出来的坑。

**1.11 商品量到 100 万要改哪里？**
四处：检索服务 BM25 换 Elasticsearch（或 PG 全文索引）+ 向量多路召回（pgvector 已在）；排序换模型服务（C++ 侧只留 RankerClient，路线图 2.1）；会话热数据迁 Redis；审计进 ClickHouse 类数仓。编排层和 LLM 层基本不动——控制面/数据面分离就是为这个准备的。

**1.12 这个项目在工程上最拿得出手的三件事？**
① 幻觉防控机制化：LLM 只做理解和表达，价格/销量等事实字段由商品库强制回填，事实类问题走知识库 grounding，从机制而不是提示词杜绝编造；② 稳定性治理：推理模型 reasoning token 挤占输出导致规划 JSON 截断，用"max_tokens 4096 + 三档容错 JSON 提取 + 温度 0 重试"三级容错把规划成功率提到 15/15；③ 质量体系：75 单测 + 离线 51 项确定性 e2e + 真模型 7 项语义 e2e + 双后端 parity 矩阵，e2e 真实抓出过 4 个行为缺陷。

## 二、C++ 控制面与 coro 协程（10 问）

**2.1 为什么基于自研 coro 协程库而不是成熟框架？**
项目规划就确定复用团队的 coro 库（`coro::Task<T>` + 线程池 + HTTP server）。我也深入到了框架边界：SSE 需要 chunked 传输支持、路由是精确键匹配不支持通配——后者直接决定了前端静态资源用扁平目录 + 每资源一条显式路由的设计。理解框架边界并在边界内设计，比"会调库"更能说明问题。

**2.2 协程在同步测试里怎么驱动？**
`coro::Task<T>` 提供 `.result()` 阻塞取结果，单测里所有异步调用（`planner.Plan(...).result()`、`tool.Execute(...).result()`）都这么驱动，不需要起事件循环。生产侧由 coro HTTP server 的线程池（4 线程）调度。

**2.3 api_server 有哪些路由？**
`POST /v1/chat`（同步 JSON）、`POST /v1/chat/stream`（SSE）、`POST /v1/feedback`（👍/👎）、`GET /v1/health`、`GET /v1/metrics`、静态路由 `/`、`/index.html`、`/styles.css`、`/app.js`。固定端口 8080，启动日志打印全部路由。

**2.4 静态文件托管怎么防路径穿越？**
两层：`ServeStaticFile` 对空路径、含 `..`、以 `/` 或 `\` 开头的请求一律 404；更根本的是 coro 路由精确 key 匹配，每个资产一条显式 `.get()` 路由，根本不存在"拼 URL 路径读文件"的入口。MIME 按扩展名表设置。前端与 API 同源托管，天然无 CORS 问题。

**2.5 HttpLlmClient 为什么有两套 HTTP 实现？**
非流式 `Chat()` 用 cpp-httplib 的 `Post`（简单、带超时）；流式 `ChatStream` 需要逐 token 增量回调，httplib 的 `Post` 没有顺手的 ContentReceiver 用法，于是手写阻塞 TCP socket + 原始 HTTP 请求，自己增量解析 SSE。代价是只支持 `http://`（https 直接返回失败，由 composer 回退非流式），内网调用可接受。

**2.6 流式 socket 有什么网络层的坑？**
localhost 双栈解析：`getaddrinfo(AF_UNSPEC)` 常先解出 `::1`，而 Python 网关只监听 IPv4，第一个 connect 失败必须**遍历全部 addrinfo** 继续试 `127.0.0.1`。另外流式 recv 超时单独放宽到 120s（流可能很长），非流式默认 45s（推理模型慢，必须大于网关上游的 20s 超时）。

**2.7 Healthy() 是怎么做的，主动探测吗？**
不是主动心跳，是**被动健康标记**：`std::atomic<bool> healthy_` 初始 true，每次 Chat/ChatStream 成功置 true、失败置 false。composer 调 LLM 前查 Healthy()，上一步规划已经发现网关挂了就不再浪费一次 compose 调用，直接走模板。检索服务同理（启动时探测一次，调用失败降级本地）。

**2.8 SSE 的并发模型是怎样的？**
api_server 的流式 handler 立刻用 `resp.stream(emitter->Writer())` 返回——Writer 是一个 coro 协程，从 emitter 的队列里等事件（mutex+cv）写 chunked；编排器在 detach 的 std::thread 里跑 `ChatStream(...).result()` 生产事件。生产者（编排线程）/消费者（io 协程）通过队列解耦，emitter 用 `shared_from_this` 保活。

**2.9 C++ 依赖怎么管理？**
CMake FetchContent：nlohmann/json、spdlog、cpp-httplib、googletest；coro 是本地库（`../coro`）；SQLite 用官方 amalgamation 源码编译（不依赖系统 SQLite，也支持把 zip 放项目根离线构建）；libpq 是可选依赖——`ENABLE_PG_CATALOG` 选项 + `find_path/find_library` 探测 PG 安装目录，找不到就无 PG 编译（源码 `#ifdef AGENT_HAVE_LIBPQ` 降级）。

**2.10 为什么 trace_id 贯穿全链路，格式是什么？**
格式 `t-<epoch>-<递增计数>`，编排器入口生成。recommendation_logs 和 llm_calls 两表都带 trace_id，一次请求的推荐审计和它触发的所有 LLM 调用（plan/compose，含重试 attempt）靠它 join；流式 final 事件和反馈表也带它，从用户一次点击能追到每一次上游调用。

## 三、Agent 编排器与状态机（13 问）

**3.1 状态机有哪些状态，怎么流转？**
SLOT_FILL（槽位补全/追问）→ RETRIEVE（召回）→ RANK（排序）→ EXPLAIN（理由）→ RESPOND（回复），异常进 FALLBACK，安全拦截进 BLOCKED。流转不由硬编码规则决定，而由 TaskPlanner 解析 LLM 输出的 `action`（clarify/retrieve/respond）驱动：LLM 每轮看到完整上下文后决定下一步，编排器负责执行和兜底。

**3.2 clarify 分支做什么？**
`is_clarifying=true`；优先用 planner 给的 `clarification_question`（含候选项），没有就用固定文案"请问您能提供更多信息吗？例如城市、人数和预算。"；然后 `UpdateContext("SLOT_FILL", slots)` 把已填槽位落库、写 assistant 轮次返回。前端按 `missing_slots` 渲染追问芯片。

**3.3 respond 分支是干什么的，曾经出过什么 bug？**
处理不需要推荐的纯对话（"谢谢"、"你好"）：直接返回 `direct_response`，空则用固定兜底文案。e2e 曾抓出一个典型 bug：用户对推荐说"谢谢"，planner 正确输出了 `action:"respond"`，但编排器没实现这个分支，掉进推荐管道，空商品触发了"暂时没有符合条件的团购"——体验完全错误。这个 bug 在 planner 和编排器的**契约接缝**上，单测测不出来，只有端到端多轮回归能暴露。

**3.4 FALLBACK 是怎么产生的？**
代码里没有专门的 FALLBACK 分支：planner 两次解析失败会把 `next_state` 置 FALLBACK；运行时 plan 里 tool_calls 为空 → 无候选商品 → composer 走短路文案。审计里 action 取值含 FALLBACK/ERROR，metrics 的 fallback_rate 统计这两类之和。

**3.5 retrieve→rank 自动链接（chained）是什么？**
当 `*_ranker` 被调用但其 arguments 里 `candidates` 缺失或为空数组时，编排器自动把上一步召回累积的商品注入为候选，并在 `tool_call` 事件里带 `"chained": true`。这样不依赖 LLM 把召回结果转发给排序器——LLM 只需声明"我要排序"，数据衔接由编排器确定性完成。planner prompt 规则 3 明确告诉模型 candidates 留空由系统注入。

**3.6 工具结果的累积规则？**
工具名以 `_ranker` 结尾判为排序器：retriever 类输出 **push_back 追加**到 accumulated_items，ranker 类输出**整体替换**（精排后的列表取代粗排列表）；kb_search 的 passages 不进商品列表，单独收集为 grounding；单个工具失败只记日志 continue，不中断整链。

**3.7 槽位是怎么合并与持久化的？**
存储层是**整段覆盖**（`UPDATE sessions SET context=?`），没有键级 merge。合并在 planner 侧完成：编排器把 `session.context` 注入 prompt 的"# 当前已填充槽位"段，LLM 结合最近 10 轮历史输出**合并后的完整槽位集合**，再整体写回。所以"第一轮说上海 3 人，第二轮只说预算 300"不会丢城市/人数——这是 `--real` e2e 的专项断言。

**3.8 历史窗口多大，在哪截断？**
编排器固定取最近 10 轮（`GetRecentTurns(session_id, 10)`）注入 prompt；prompt_builder 自己不截断、整段拼入"# 历史对话"。截断职责在编排层，prompt 层只做格式化。

**3.9 BLOCKED 的请求写不写会话记忆？**
写。输入被拦截后 refusal_reply 作为 assistant 轮次、用户原文作为 user 轮次都写入记忆，保持 transcript 连贯（下一轮模型看到的对话是完整的）；但 BLOCKED 轮**跳过 planner**，所以 llm_calls 里 plan 行数 = 总轮数 - 拦截轮数（e2e S6 精确断言了 7 请求 6 次 plan）。

**3.10 外层壳 / 内层拆分是什么设计？**
`ChatStream` 拆成外层壳和内层 `ChatStreamInner`：内层是纯业务（guard→plan→工具→compose）；外层只做两件事——计时和写库，且是**单一出口**：无论内层走 blocked/clarify/respond/retrieve/error 哪条路径，返回前统一写一行 recommendation_logs + 每条 LLM 调用一行 llm_calls。非流式 `Chat()` 就是 `ChatStream(req, nullptr)`。这个拆分让审计覆盖 5 条返回路径而业务代码零侵入。

**3.11 grounding 怎么组装传递？**
kb_search 的每条 passage 被渲染成"【标题】内容（来源：xx）"，编号拼成 grounding_text 作为第 5 个参数传给 composition prompt；prompt_builder 把它拼在商品列表之后，标题是"# 参考知识（回答问题时以此为准，不要编造）"，grounding 为空则整段省略。流式路径还会先发一个 `grounding` 事件让前端实时展示"回答依据"面板。

**3.12 空商品但有 grounding 时为什么还能回答？**
composer 的短路条件是"items 为空**且** grounding 为空"才返回"暂时没有符合条件的团购"。纯知识问题（"能开发票吗"）走的是 retrieve action + 只调 kb_search，商品为空但有 grounding，于是让 LLM 基于知识段落作答——planner prompt 规则 4 明确：事实/政策类问题不受槽位缺失限制。

**3.13 输入拦截在链路的什么位置，输出脱敏在什么位置？**
输入护栏在 planner **之前**——被拦截的请求根本不消耗 LLM 调用；输出脱敏在 compose **之后**、写库和返回之前，作用于回复正文和每个商品的 title/reason/tags。两个位置都是"影响面最大、成本最低"的点：输入侧省下 LLM 调用，输出侧保证落库和展示的都是脱敏文本。

## 四、TaskPlanner 与 Prompt 工程（12 问）

**4.1 planner 的输入输出契约？**
输入：system 固定"You are a task planner..."+ user 段（槽位说明、规则、当前已填充槽位、历史对话、用户当前输入）。输出必须是纯 JSON：`{"action":"clarify|retrieve|respond", "slots":{...}, "missing_slots":[...], "clarification_question":"...", "tool_calls":[{"tool_name","arguments"}]}`。解析后 call_id 由 `"tc-" + hash(arguments_json)` 生成。

**4.2 槽位有哪些，budget 的规则是什么？**
city（必填）、district（可选）、category、budget、people、time、preference、taboo。budget 是**总预算**：prompt 明确写"人均 100 且 3 人 → budget=300"，把换算责任交给模型并给了确定规则，避免有时当人均有时当总价。

**4.3 六条核心规则？**
① city/category/budget 任一缺失或低置信 → clarify；② 信息足够 → retrieve + deal_retriever；③ 有预算/人数/禁忌可追加 deal_ranker，candidates 留空由系统注入；④ 事实/政策类问题（发票/预约/退款/包间/停车/忌口/营业时间/核销等）必须追加 kb_search，纯事实问题 action 仍为 retrieve 且 tool_calls 只含 kb_search，不受规则①限制；⑤ 不编造；⑥ 必须输出合法 JSON、不要 Markdown 围栏。

**4.4 为什么"纯知识问题也走 retrieve action"这条规则是 e2e 逼出来的？**
原来 prompt 只在"推荐商品"语境下提 kb_search，模型对"能开发票吗"直接 respond 跳过检索，答案靠编。e2e `--real` 的 `R.turn3.kb_search_called` 断言暴露后，规则 4 改成：纯事实问题同样 action=retrieve、tool_calls 只放 kb_search。这是"prompt 缺陷 → e2e 断言 → 固化规则"的典型循环。

**4.5 采样参数怎么设的，为什么？**
规划：首次 temperature=0.3、max_tokens=**4096**。4096 是关键修复——推理模型（deepseek-v4-flash）先烧大量 reasoning token，默认 1024 时规划 JSON 在 `"tool_name"` 键名处被截断，约 1/3 请求因此 FALLBACK。compose：temperature=0.6、max_tokens=2048，超时单独限 20s。

**4.6 JSON 容错解析的三档递进？**
共享函数 `ExtractJsonObject`：① 整体直接 `json::parse`，必须是 object；② 找第一个 ` ``` `，去掉开头可选的 `json` 字样、截到最后一个 ` ``` `，trim 后解析（对付 Markdown 围栏）；③ 取原文第一个 `{` 到最后一个 `}` 的子串解析（对付散文里嵌 JSON）。三档全败返回 nullopt。composer 的 `TryParseComposition` 复用同一函数。

**4.7 重试策略？**
最多 2 次 attempt：第 0 次解析失败 → 把 temperature 降为 **0.0** 做确定性重试（同一个错误不会因为采样随机性再犯一次，且省得无效多次重试）；第 2 次仍失败 → 记 error 日志、`next_state=FALLBACK`。每次 attempt 都记一条 `LlmCallInfo`（purpose=plan、status=success/parse_error、attempt 序号）进审计。

**4.8 离线 stub 时 planner 怎么工作？**
planner 自己没有内置规划器——`HttpLlmClient::Chat` 在 base_url 为空时返回硬编码的三分支确定性 plan JSON：从 user 消息按标记"# 用户当前输入"截出真实输入；含"海鲜"+"上海"→ retrieve（固定槽位：上海/海鲜/300/3人/今晚 + retriever + ranker）；含"吃"或"想"→ clarify；否则 respond 固定寒暄。离线 e2e 的 51 项确定性断言就建立在这三分支上。

**4.9 为什么不让 LLM 直接输出最终推荐列表？**
幻觉防控：LLM 只做**理解**（意图/槽位/计划）和**表达**（把排好序的商品写成自然语言），不碰数据。价格、销量、评分等事实字段全部来自商品库回填，composer 的 system 词再钉一遍"价格/折扣/商家等数据必须与给定商品一致，禁止编造"。交易场景价格错了就是纠纷，这是合规底线。

**4.10 composer prompt 的结构？**
非流式：Role（团购推荐助手）→ 7 条规则（数据一致、结合人数/预算/偏好/禁忌、先总览再点亮点、空列表给建议、JSON 输出、item_reasons 的 key 必须是 item_id、有参考知识必须依据它）→ 输出格式 `{reply, item_reasons}` → 用户需求/槽位/Top 商品（≤10 条已排序）→ grounding 段 → "请直接输出 JSON"。流式版改为"直接输出自然语言，不要 JSON"。

**4.11 为什么 compose 送 LLM 的商品上限是 10 条？**
`kMaxComposeItems=10`：prompt 里商品越多 token 越贵、模型越容易漏看后面的；top_n 默认只取 3，10 已经留了余量。这也是成本控制手段之一（配合审计表按 plan/compose 分开归因 token）。

**4.12 prompt 里"当前已填充槽位"段起什么作用？**
编排器把 `session.context` 整段注入，模型每轮基于"历史对话 + 已填槽位 + 新输入"输出**全量槽位**，存储层再整段覆盖。这把多轮槽位延续的责任放在最能理解上下文的地方（LLM），存储层保持哑实现——简单且被 `--real` 回归验证过。

## 五、召回排序工具链（DealCatalog / Retriever / Ranker，12 问）

**5.1 DealCatalog 的三源回退链？**
构造函数 `DealCatalog(json_path, pg_dsn="")`：① pg_dsn 非空 → libpq 直连 `groupbuy_items`（source="postgres"）；② 失败 → JSON 文件（source="file:path"，支持 `{"deals":[...]}` 或裸数组两种格式）；③ 再失败 → 内置 8 条兜底数据集（source="builtin"，强制 loaded=true）。默认参数让全部旧调用点行为不变；api_server 用 `CATALOG_BACKEND`（默认 json，保 e2e 确定性）+ `PG_DSN` 接线。

**5.2 LoadFromPostgres 的实现要点？**
libpq C API：`PQconnectdb` → `PQstatus` 检查 → `PQexec`（固定 14 列 SELECT，`ORDER BY item_id` 与 Python 侧同列同序）→ `PGRES_TUPLES_OK` 检查 → 逐行文本模式取值：`strtod`/`strtoll` 转数值，`PQgetisnull` 处理 NULL（district/original_price → JSON null），tags JSONB 文本 `json::parse(allow_exceptions=false)` 失败给空数组 → `PQclear` + `PQfinish`。空结果集**视为失败**（更可能是没播种）回退下一级。

**5.3 为什么空结果集要视为失败而不是空目录？**
故障可区分性：表为空几乎必然是运营事故（没跑 pg_seed），而 JSON 文件/内置兜底里有可用数据。宁可回退也不服务空目录——降级链的原则是"用次优但正确的数据"，不是"忠实地空着"。

**5.4 DealRetriever 支持哪些过滤参数？**
city（必填）、category、district、min_price/max_price（默认 0/1e9）、people（0=不限）、keywords、top_k（默认 20，≤0 归一为 20）。city/category/district 精确相等；价格在区间内；people 做区间匹配。

**5.5 people 区间匹配的语义有什么讲究？**
双守卫：只有当 deal 同时有 `min_people>0` 且 `max_people>0` 时才要求 `people ∈ [min,max]`；区间为 (0,0)（无限制）的套餐永不被人数过滤掉。这个语义在 C++ 本地过滤、PG SQL 下推（`NOT (mn>0 AND mx>0 AND NOT (mn<=p AND p<=mx))`）、JSON 后端三处逐条镜像，parity 矩阵就是验证这种边角一致性的。

**5.6 本地相关性打分公式？**
无关键词：`0.6*rating_norm + 0.4*discount`；有关键词：`0.5*relevance + 0.3*rating_norm + 0.2*discount`。rating_norm=rating/5；discount=(original-price)/original 钳制 [0,1]；relevance=命中 token 数/总 token 数，token 按空格和中英文标点切分，匹配域是 title+category+description+tags 拼接。服务健康时整个打分被检索服务的排序取代，本地公式只是降级路径。

**5.7 检索服务委托与降级的判断？**
`retrieval` client 存在且 `Healthy()` 为 true → 把 query/city/category/district/价格区间/people/top_k 全部转发 `SearchDeals`，直接采用其排序（BM25/RRF）；服务调用失败 → warn 并回落本地子串匹配。健康标记同样是被动的：每次调用成败更新，不做心跳。

**5.8 DealRanker 的多因子公式？**
`score = 0.35*rating_norm + 0.25*popularity + 0.25*price_fit + 0.15*discount`。popularity = sold_count/候选集最大销量（下限 1）；price_fit：price≤budget → 1.0，超预算线性衰减 `max(0, 1-(price-budget)/budget)`，budget=0 恒 1.0。top_n 默认 3。

**5.9 taboo 和 budget 的处理区别？**
taboo 是**硬过滤**：taboo 串同样分词，候选命中任一 taboo token 即整条剔除（"不要辣的"→ 含"辣"的全部出局）。budget 是**软惩罚**：超预算不剔除而是 price_fit 线性衰减——因为"预算 300"通常不是刚性上限，完全剔除可能把 310 元的好选项冤杀。一硬一软是有意的语义区分。

**5.10 为什么 ranker 不沿用检索服务返回的 score？**
粗排和精排目标不同：检索 score 衡量**文本相关性**（BM25/向量相似度），精排要优化**业务目标**（契合预算、口碑、热度、折扣）。所以 ranker 从不读候选的 score 字段，用四因子公式重算并覆盖。这个设计带来一个重要推论：检索 score 的语义完全自由——向量 RRF 融合改归一化方式不影响下游，向量召回的价值是**候选集扩展**（把语义相关商品送进候选），最终顺序由 ranker 决定。

**5.11 reason 字段哪来的？**
三级来源：工具默认用 `BuildReason` 生成"评分 X.X · 销量 N · 约 Y.Y 折"；LLM compose 的 `item_reasons` 按 item_id 精确匹配回填覆盖（空串不回填）；输出脱敏对 reason 同样生效。所以卡片上的推荐理由既是数据驱动的又可以是 LLM 润色的。

**5.12 Mock 工具去哪了？**
旧的 `MockRetriever/MockRanker`（写死 4 条数据）作为 Phase-0 参考实现保留在源码里，但默认不再注册；当前唯一接线的是真实目录后端。保留它们是因为接口契约（ToolRegistry、ToolCall/ToolResult）是以它们为蓝本稳定的。

## 六、检索服务：BM25 + 向量 RRF + PostgreSQL（15 问）

**6.1 服务职责与端点？**
两个语料三个端点：deals（商品召回）和 kb（知识库 22 条 FAQ/政策）。`GET /v1/health`（状态+后端+向量状态）、`POST /v1/retrieve/deals`（结构化过滤 + 文本排序）、`POST /v1/retrieve/kb`（纯 BM25）。响应形状是 C++↔Python 的契约冻结区。

**6.2 BM25 怎么实现的？**
纯 stdlib 自研。分词：ASCII 词按 `[A-Za-z0-9]+` 提取小写化，剩余 CJK 部分做**重叠字符 bigram**（"小龙虾"→小龙/龙虾）。IDF 用 BM25+ 恒正变体 `log(1+(n-df+0.5)/(df+0.5))`；评分 `idf*tf*(k1+1)/(tf+k1*(1-b+b*dl/avgdl))`，k1=1.5、b=0.75，dl 或 avgdl 为 0 用 1 兜底。语料启动时一次性构建内存倒排（term→{doc:tf}），不热加载。

**6.3 为什么 bigram 而不是 jieba？**
零依赖（项目 Python 侧除 psycopg/fastembed 外纯 stdlib）、确定性、对中文检索精度召回兼顾，且不需要词典维护。团购标题短文本场景下 bigram 的召回优势（"龙虾"能命中"小龙虾"）比精确分词更重要。deal 索引文本 = title+category+description+tags，与向量 embedding 的文本**完全同源**（共享 dealtext.py）。

**6.4 双后端架构怎么保证逐字节一致？**
五个手段：① PG 加载 `ORDER BY item_id` 与 deals.json 文件序一致；② SQL 过滤只回 item_id，映射回 doc_idx 后按 doc_idx 排序，保证 rating 兜底稳定排序的并列序一致；③ DECIMAL 列单点 `_to_float` 转换；④ JSONB tags 的 None 归一为 `[]`；⑤ people/价格/NULL district 的过滤语义在 SQL 里逐条镜像（含 max_price=0 必须过滤而非忽略、people 双守卫）。`test_pg_retrieval.py` 20 例 diff 矩阵逐字节验证。

**6.5 为什么过滤下推只 SELECT item_id？**
两个原因：避免 psycopg 的 Decimal/date 类型序列化问题（响应体由内存中的 dict 构造，类型早已归一）；网络和解码开销最小——5320 行过滤结果只传 id 列表，排序在内存做。这也让 SQL 层和排序层职责清晰：SQL 管"哪些活着"，Python 管"怎么排"。

**6.6 向量通道的完整架构？**
离线：`scripts/pg_embed.py` 用 fastembed（ONNX 运行时，无 torch）加载 bge-small-zh-v1.5，把 deal_text 批量（64/批）编成 512 维向量，`UPDATE ... SET embedding=%s::vector` 写入 PG（默认只补 NULL 行增量）。查询时：query 同模型编码 → `embedding <=> %(vec)s::vector` 余弦距离 ANN（HNSW 索引，vector_cosine_ops）→ 与 BM25 候选 **RRF 融合**。结构化过滤同样下推到向量 SQL（同一个 `_pg_filter_where`）。

**6.7 RRF 融合的具体参数与公式？**
`RRF_K=60`；每通道候选池 `max(top_k*4, 40)`；`rrf[doc] += 1/(60+rank)`（rank 从 1 起，缺席通道贡献 0）；归一化除以双通道理论最大值 `2/(60+1)` → 双榜第一≈1.0、单榜第一≈0.5，score ∈ (0,1]；排序键 `(-rrf, doc_idx)`——分数降序、doc_idx 升序破并列，截 top_k。

**6.8 为什么选 RRF 而不是加权分数融合？**
BM25 分数和余弦距离**量纲不可比**（BM25 无上界、cosine ∈ [-1,1]），加权融合需要调归一化超参且对分布敏感；RRF 只用排名，天然无量纲、零超参（k=60 是文献标准值）、对单通道噪声鲁棒。缺席通道不贡献分数的设计也让"BM25 无命中但向量有命中"的同义词场景自然成立。

**6.9 向量通道的降级设计？**
三级门控，全部失败静默降级纯 BM25：① `RETRIEVAL_VECTOR=on` 且 backend=postgres 才尝试；② 启动时 `_init_vector`：fastembed 可导入 + 模型加载成功 + `embedding IS NOT NULL` 行数>0（这条顺带探测向量列/扩展是否存在）；③ 请求级 try/except：向量查询当次失败仅本次回退。health 的 `vector`/`vector_model` 字段可观测当前状态。

**6.10 向量开启后的行为变化是什么，为什么接受？**
非空查询几乎总有结果（余弦最近邻永远存在），"BM25 无命中→评分排序兜底"只在结构化过滤集为空时触发。这是有意为之：垃圾 query 返回语义最近邻比返回评分最高的无关商品更接近用户意图，且 test_pg_vector 用"垃圾查询返回 5 条 score∈(0,1] 的向量结果"固化了这个行为。

**6.11 为什么选 fastembed + bge-small-zh 而不是 OpenAI embedding 或 torch 方案？**
四个约束的交点：中文场景（bge 系列中文 benchmark 强）、离线确定性（模型本地加载，无 API 依赖/费用/延迟）、依赖纪律（ONNX 运行时无 torch，几百 MB 依赖变几十 MB）、维度适中（512 维 × 5320 行，存储和 ANN 都轻）。OpenAI embedding 把数据发外网且每次 reseed 都要花钱，不符合"数据面可控"原则。

**6.12 embedding 文本为什么要抽共享模块？**
`deal_text()` 原本在 main.py，但 main.py **import 时就连 PG**，pg_embed.py import 它会触发连接。抽出 `retrieval_service/dealtext.py`（deal_text + vec_literal）两边共享，保证"embed 的文本"与"BM25 语料"永远同源——否则向量通道和 BM25 通道索引的不是同一个东西，融合就失去意义。

**6.13 国内网络下模型下载的坑？**
两个：HuggingFace 直连不通要 `HF_ENDPOINT=https://hf-mirror.com`；镜像不支持 hf-xet CAS 协议（401）还要 `HF_HUB_DISABLE_XET=1`。都写进了 sql/README §6。

**6.14 rating 兜底排序的细节？**
空 query 或全通道无命中 → 按 rating 降序（稳定排序，依赖语料顺序保证并列一致），score=rating/5，截 top_k。与 C++ 无关键词行为对齐。这是 e2e 抓出来的坑修的：query="包间"无文本命中时返回空推荐，体验远不如给评分最高的候选。

**6.15 PG 连接池与健康观测？**
psycopg_pool：min 1/max 4、autocommit、connect_timeout=5、`open(wait=True)`。health 返回 `status/corpora/deal_count/kb_count/backend/vector/vector_model/tokenizer`——backend 指示 PG 还是降级 json，vector 指示向量通道状态，运维一眼定位降级发生在哪层。

## 七、LLM 网关（10 问）

**7.1 为什么要一个网关，C++ 直连 DeepSeek 不行吗？**
三个职责让它值得独立：① **模型名权威**——C++ 发占位 `gpt-4o-mini`，网关用 `LLM_MODEL` 覆盖，换模型不改 C++；② **凭证隔离**——API key 只在网关的 `.env.local`，C++ 侧零密钥；③ **失败回退**——上游任何异常（HTTPError/超时/解析失败）回退确定性 stub，整条链路不挂。另外 Python 处理 OpenAI 兼容协议比 C++ 迭代快得多。

**7.2 stub 模式的分支逻辑？**
三分支确定性规划（`make_plan`）：用户文本同时含"海鲜"和"上海"→ retrieve（固定槽位 + deal_retriever + deal_ranker）；含"吃"或"想"→ clarify（missing city/budget/people）；否则 respond 固定寒暄。用户文本从最后一条 user 消息按标记"# 用户当前输入"截取。无 `LLM_API_KEY` 即 stub 模式。

**7.3 real 模式怎么透传？**
POST 到 `LLM_API_BASE + /chat/completions`，Bearer 头；转发体只含 model/messages/temperature（默认 0.3）/可选 max_tokens；**model 永远被 LLM_MODEL 覆盖**，客户端传的被丢弃；响应原样 relay（只回填 model 字段）。`LLM_TIMEOUT_SECS` 默认 20s。

**7.4 流式怎么透传？**
`stream_real_llm` 给上游加 `"stream": true` + `Accept: text/event-stream`，然后 `resp.read(4096)` 循环把**原始 SSE 字节逐块** `wfile.write + flush`——字节级透传不解析不重打包，上游帧格式什么样客户端就收什么样，最后追加 `[DONE]`。stub 流式则把整个 plan JSON 作为单个 delta 发出再发 `[DONE]`。

**7.5 网关的 SSE 响应为什么用 Connection: close 而不是 chunked？**
Python stdlib 的 `http.server` 是 HTTP/1.0，自己手写 `text/event-stream` 头后靠**连接关闭**定界流结束——简单可靠，客户端（C++ 裸 socket 解析器）也是按 EOF flush 残余缓冲实现的。两端是自己人，协议从简。

**7.6 env 加载的坑？**
`_load_env_file` 用 `os.environ.setdefault`——已存在的键永不覆盖，且 `.env` 先于 `.env.local` 加载，所以**同名键 .env 赢**（先到先得，与"local 覆盖全局"的直觉相反）。纪律：每个键只在一个文件里定义；真实环境变量最高优先。

**7.7 stub 响应的 usage 字段怎么来的？**
字符数冒充 token 数（`prompt_tokens=len(user_message)`）——stub 不调真模型没有真实 usage，但响应形状必须和 OpenAI 一致（C++ 侧会解析 usage 写审计），用字符数占位保契约。审计口径上 stub 模式的 token 数本就没有意义。

**7.8 网关挂/慢的时候 C++ 侧表现？**
非流式：httplib 45s 超时（大于网关上游 20s，保证网关先超时回退 stub 而不是 C++ 先断）；失败后 Healthy()=false，composer 不再尝试 LLM 直接模板。流式：socket 失败返回 `streamed=false`，composer 回退模板按行切 delta，用户仍看到流式线序。

**7.9 health 返回什么，有什么用？**
`{status, mode: "real-llm"|"deterministic", model}`。面试演示时用来一句话证明"现在跑的是真模型不是 stub"——配合发一条 stub 无法匹配的查询（如"火锅/北京/4人/500"），stub 只会 clarify，真模型能正确解析出完整工具计划。

**7.10 为什么 stub 三分支选"海鲜+上海"这些关键词？**
它是 e2e 的确定性锚点：离线回归需要一个**不依赖 LLM 也能走通完整 retrieve→rank→compose 链路**的输入，"上海 3 人吃海鲜预算 300"恰好覆盖全部槽位 + 类目，三分支（完整→追问→寒暄）覆盖三条 action 路径。换关键词 = 重写 e2e，所以这些词是测试契约的一部分。

## 八、流式 SSE 与 Web 前端（11 问）

**8.1 SSE 事件序列全集？**
`started`（带 session_id）→ `input_guard` → `planning` → `plan`（带 next_state/missing_slots/tool_count）→ `tool_call`/`tool_result` 成对（tool_call 带 chained 标记）→ 可选 `grounding`（passage_count）→ `composing` → `delta`×N（逐 token）→ `final`（完整 12 字段商品 + grounding）或 `error`。

**8.2 传输层怎么实现的？**
HTTP `Transfer-Encoding: chunked` + `Content-Type: text/event-stream; charset=utf-8`。每个事件一帧：`data: {"event":..., "data":...}\n\n`——事件名放在 JSON 信封里而不是 SSE 的 `event:` 行，前端只解析一种格式。JSON 序列化用 `error_handler_t::replace` 保证非法 UTF-8 不炸流。

**8.3 StreamEmitter 为什么设计成回调接口？**
编排管线只面向 5 个纯虚方法编程（Emit/EmitDelta/Finish/Error/IsClosed），不关心传输格式：非流式路径传 nullptr，单测注入 fake 断言事件序列，生产用 SseStreamEmitter。事件进队列（mutex+cv），Writer 协程等 cv 后整批 swap 出队写 chunked——生产消费解耦。

**8.4 delta 和 final.reply 是什么关系？**
delta 是 LLM 原始增量；final.reply 是**输出脱敏后**的最终文本。LLM 文本不含敏感信息时二者逐字节一致（已实测 200+ delta 拼接验证）；若含手机号之类，final 是打码版——落库和卡片用 final，流式过程的 delta 只做展示。

**8.5 流式的降级链？**
真 LLM token 流（`streamed=true`）→ 网关/socket 失败（`streamed=false`）→ composer 把**确定性模板按行切 delta** 推送，前端打字机效果和事件线序完全不变，用户感知不到降级。这是"流式是体验特性不是正确性依赖"的设计。

**8.6 前端为什么用 fetch + ReadableStream 而不是 EventSource？**
原生 EventSource 只支持 GET，而 `/v1/chat/stream` 是 POST（请求体带消息和 session）。所以前端用 fetch 拿 `response.body.getReader()`，手动按 `\n\n` 切块、剥离 `data: ` 前缀解析 JSON 帧。

**8.7 前端有哪些超出"裸 API"的体验设计？**
流式打字机；可折叠"思考过程"面板（实时展示各工具调用/完成状态）；商品卡片（价格/折扣/评分/销量/区县/tags/理由）；"回答依据"面板（grounding 段落）；追问芯片（按 missing_slots 快捷填充城市/人数/预算/类目）；session_id 存 localStorage 跨刷新续聊；中途停止生成（AbortController）；流式失败自动降级 `/v1/chat` 一次性回复；在线状态点轮询 health。

**8.8 流式 compose 的 token 为什么记 0？**
上游 SSE 流式响应不返回 usage 字段（没开 `stream_options.include_usage`），所以流式 compose 的 llm_calls 行 prompt/completion_tokens 记 0——是**口径而非丢失**，审计注释写明 "recorded honestly"；metrics 的 token 汇总只反映非流式调用。

**8.9 final 事件的 items 为什么是 12 个字段？**
商品卡片要展示评分、销量、折扣、区县，`RecommendationItem` 扩展了 sold_count/rating/district/score/reason，final 对齐 `/v1/chat` 的完整字段集。曾经只有 8 个字段，为了卡片补齐——e2e S2 逐项断言 12 字段防回归。

**8.10 SSE 解析器怎么处理脏数据？**
C++ 侧：`\r\n\r\n` 分头检查后按 `\n\n` 增量切事件，逐行找 `data:` 前缀、跳过 `[DONE]`，畸形 chunk try/catch 忽略（best-effort），EOF flush 残余缓冲。原则：单帧损坏不毁整条流。

**8.11 流式路径下编排器在哪个线程跑？**
handler 立即 `resp.stream(emitter->Writer())` 返回，编排器在 detach 的 std::thread 里同步驱动 `ChatStream(...).result()` 生产事件。这样 coro 的 io 线程不被阻塞，队列解耦让慢消费（网络差）不压垮编排。

## 九、会话记忆与反馈闭环（10 问）

**9.1 三张表的 schema？**
`sessions`（session_id PK、user_id、current_state 默认 SLOT_FILL、context JSON 字符串、created/updated_at）；`turns`（rowid、session_id FK→CASCADE、role、content、created_at，索引 (session_id, rowid)）；`feedback`（rowid、session_id FK→CASCADE、trace_id、item_id 空=整条回复、feedback_type、comment、created_at）。WAL + `foreign_keys=ON`。

**9.2 context 槽位的合并语义？**
存储层整段覆盖（`UPDATE sessions SET current_state=?, context=?`），不做键级 merge——合并在 planner 侧由 LLM 完成（历史 + 已填槽位 → 全量槽位 → 整体写回）。职责划分：存储哑、模型聪明。`sqlite3_changes()==0` 说明 session 不存在，报错。

**9.3 session_id 怎么生成，怎么续聊？**
`s-<epoch>-<原子计数>`。客户端（前端 localStorage / e2e 变量）持有 session_id 并在后续请求带上；`GetOrCreateSession` 对已有 id 先 SELECT 命中即续，否则新建。跨进程重启后同库同 id 继续对话——e2e S3 专门杀掉 server 用同一 DB 重启验证。

**9.4 GetRecentTurns 怎么实现？**
`ORDER BY rowid DESC LIMIT ?` 取最近 N 条后 `std::reverse` 恢复时间序。编排器固定传 10。索引 (session_id, rowid) 让这个查询走索引。

**9.5 反馈接口的校验与未知 session 处理？**
`/v1/feedback`：session_id 必填、feedback_type 只允许 like/dislike，否则 400；未知 session 由 FK 约束拒绝（insert 失败 → 400）。AppendTurn 同语义。SQLite 和 InMemory 双实现对"未知 session 是错误"行为一致——单测各测一遍。

**9.6 为什么反馈表放 sessions 库而不是观测库？**
feedback 有外键指向 sessions（CASCADE 删会话连带删反馈），必须在同库；观测库无外键需求。反馈还带了 trace_id——既能按会话维度看满意率，也能 join 回具体哪次推荐。

**9.7 反馈数据现在被谁消费，将来喂给谁？**
现在：`/v1/metrics` 用 ATTACH 会话库算满意率（like/(like+dislike)），`evaluate.py` 输出满意率和被 👎 最多的商品 Top5。将来（路线图 2.1）：item 级反馈做 CTR/CVR 特征进 item_features 表，训练 LightGBM 排序模型——反馈闭环是排序学习的数据基础，这是先埋点的原因。

**9.8 存储接口怎么设计的？**
`SessionMemoryStore` 5 个协程方法：GetOrCreateSession / AppendTurn / GetRecentTurns / UpdateContext / AppendFeedback。Sqlite 实现单连接 + mutex 串行化（SQLite 写串行本就够），头文件只前向声明 `struct sqlite3` 不暴露 C API。`SESSION_STORE=memory` 可切内存实现（测试/演示）。

**9.9 多轮中"覆盖语义"踩过什么坑？**
context 是整体覆盖的，respond 类型的轮次会把槽位清空——这是设计内行为，但要求 planner 每轮都必须从历史重建完整槽位，而不是只做增量。e2e `--real` 的 `R.turn2.no_reask_city_people` 就是防这个回归：第二轮只补预算时不得重问城市/人数。

**9.10 会话层怎么演进到多实例？**
热数据迁 Redis（短期 TTL，最近 N 轮 + 当前槽位），冷数据留 PostgreSQL（持久化，对齐现有 schema）；接口 5 个方法不变，换一个 SessionMemoryStore 实现即可——接口设计时已经把这一天算进去了。

## 十、观测、指标与离线评估（10 问）

**10.1 两张审计表记什么？**
`recommendation_logs`：trace_id、session_id、请求原文、action、slots_json、item_count、Top5 商品（只存 item_id+score）、response_text、grounding_count、compose_mode、latency_ms。

`llm_calls`：trace_id、purpose（plan/compose）、model、prompt/completion_tokens、latency、status（success/parse_error/template_fallback/stream_fallback）、attempt（重试序号）。trace_id 串联两表。

**10.2 什么是"回传式"观测设计？**
不在 planner/composer 的签名里穿 store 指针：`Plan.llm_calls`、compose 结果把 LLM 调用元数据**作为返回值的一部分**带回编排器，由外层壳统一写库。组件签名零改动、组件保持纯业务可测，审计只有编排器一个写入点。

**10.3 写库失败会怎样？**
fire-and-forget：写审计失败只 warn 不抛——观测绝不能影响主链路可用性。观测库单独 `busy_timeout=2000`（会话库没有，因为会话写是主路径必须立即可见，审计可以等等）。

**10.4 /v1/metrics 聚合哪些指标？**
by_action 分布、fallback_rate（FALLBACK+ERROR/总量）、empty_retrieve_rate（retrieve 但商品和 grounding 都空）、avg/p95 延迟、grounded_requests、LLM 调用数与 token 汇总、反馈满意率（ATTACH 会话库算 like/(like+dislike)，ATTACH 失败则整段省略）。

**10.5 p95 怎么算的？**
SQL nearest-rank 近似：`ORDER BY latency_ms LIMIT 1 OFFSET max(int(count*0.95)-1, 0)`。不维护分位数 Sketch，量级下 SQL 排序足够——观测实现也遵循"按当前规模选型"。

**10.6 compose_mode 有哪些值，说明什么？**
`llm_stream`（真 token 流）、`llm`（非流式 LLM）、`template`（模板回复）、`short_circuit`（空商品空 grounding 的短路文案）、`none`（clarify/BLOCKED 等没走 compose 的路径）。这个字段让你能从审计直接读出"多少比例的回复是真 LLM 生成的"。

**10.7 evaluate.py 输出什么？**
读 observability.db + sessions.db 出离线报告：action 分布、FALLBACK/空推荐率、追问后续答率、延迟 avg/p50/p95、LLM token 消耗、grounding 触发率、反馈满意率、被 👎 最多商品 Top5。定位是"每周跑一次的健康检查"。

**10.8 一次请求最多产生几行审计？**
1 行 recommendation_logs + N 行 llm_calls（plan 最多 2 次 attempt + compose 1 次，BLOCKED 轮 0 行 plan）。e2e S6 精确断言过：7 请求 → 7 行 rec_logs、6 次 plan（1 轮被拦截）、2 次 compose。

**10.9 审计数据能回答哪些运营问题？**
"系统多稳"（fallback_rate）、"追问有没有用"（追问后续答率）、"RAG 触发频率"（grounded_requests）、"钱花哪了"（plan/compose 分开的 token 归因）、"用户满不满意"（满意率 + 👎 Top5 商品）。设计审计字段时就是按这五个问题反推的。

**10.10 为什么观测独立成库而不是塞进会话库？**
写模式不同：会话是"每请求两次小写 + 偶尔读"，审计是"每请求多行追加写、批量聚合读"。同库会让审计的高频写与会话读写竞争锁；独立库还能单独备份、单独设保留策略，ATTACH 解决跨库 join 就够了。

## 十一、安全护栏（10 问）

**11.1 护栏的总体定位？**
规则式、确定性、**零额外 LLM 调用**，接入编排器的输入（规划前）和输出（返回前）两个点。构造函数传 SafetyGuard 启用、传 nullptr 跳过（默认参数不破坏调用方）。LLM 版深层检查（InputSafetyPrompt 已写好）留作未来增强。

**11.2 输入拦截哪三类，顺序？**
① too_long：`user_message.size() > 500` 字节（公开可调）；② prompt_injection：ASCII 部分转小写后子串匹配、中文逐字匹配；③ banned_topic：原文子串匹配。按这个顺序短路，命中即返回对应 risk_type 和固定中文拒答文案。

**11.3 注入话术清单有什么？**
英文："ignore previous instructions"、"forget your instructions"、"system prompt"、"reveal your prompt"、"developer mode"、"jailbreak"、"dan mode"、"act as "（带空格）、"no restrictions" 等；中文："忽略之前的指令""无视上面的""覆盖你的指令""你现在的身份""扮演一个""没有任何限制""输出你的系统提示""系统提示词""越狱""解除限制"。

**11.4 违禁主题和输出违禁词为什么不一样？**
输入拦截主题表：赌博、毒品、色情、枪支、爆炸、洗钱（6 个，宽进——宁拦错）；输出违禁词表：赌博、毒品、色情（3 个，窄出——商品标题里出现"爆炸"可能是"爆炸口味"的误伤风险，输出侧只掩码真正不能出现的词）。输入求召回、输出求精度。

**11.5 输出脱敏的四个正则与顺序讲究？**
按**先长后短**：身份证 `\d{17}[\dXx]` → 16-19 位长数字（银行卡）→ 手机号 `1[3-9]\d{9}` → 邮箱。顺序错了 11 位手机号正则会先吃到 18 位身份证的中间一段，剩下的就不再是合法身份证格式——先匹配长模式保住完整识别。

**11.6 违禁词怎么替换？**
从左到右找最早出现位置替换为 `***`，pos 前进 3 字节（就是 `***` 的长度）继续扫。作用于回复正文；`SanitizeItems` 再对每个商品的 title/reason/tags 逐个脱敏——商品数据也是"输出"。

**11.7 被拦截请求的返回形态？**
`next_state="BLOCKED"` + 固定拒答文案（如注入类："抱歉，我只能帮您推荐团购套餐，无法处理这类请求。您可以告诉我城市、用餐人数和预算。"）；items 为空；user/assistant 两轮照常写记忆保持 transcript 连贯；跳过 planner 不消耗 LLM。e2e S4 断言拦截后**会话仍可用**。

**11.8 为什么不用 LLM 做安全审核？**
成本（每请求多一次调用）、延迟（链路上再加一秒级 RT）、确定性（正则可单测、可回归，模型判断不可复现）。规则护栏先挡住 95% 的显式攻击；LLM 深层审核留给真正需要语义判断的场景，且可以异步做。安全层和生成层解耦。

**11.9 除了护栏还有哪些安全设计？**
静态文件路径穿越防护（`..`/绝对路径 404 + 精确路由）；反馈接口参数校验 + FK 约束；凭证全部 gitignore（`.env.local`）；C++ 侧零密钥（key 只在网关）；composer system 词禁止编造事实字段（防幻觉也是广义的输出安全）。

**11.10 护栏的测试怎么做的？**
11 个单测：正常输入放行（不误伤）、中英注入各拦截、违禁话题拦截、超长拦截、手机号/邮箱/身份证打码、正常文本不误伤、商品推荐理由脱敏。加上 e2e S4 的端到端拦截 + 会话续用断言。"不误伤"用例和"拦得住"用例一样多——护栏的最大风险是误杀正常用户。

## 十二、测试体系与数据生成（13 问）

**12.1 测试金字塔长什么样？**
四层：75 个 gtest 单测（组件契约）；离线 e2e 51 项（C++ 内置 stub，秒级确定性）；真模型 e2e 7 项（语义行为）；专项矩阵（双后端 parity 20 例 + 向量语义断言）。哲学：越下层越快越确定，越上层越接近真实但允许一次重试对抗模型随机性。

**12.2 75 个单测怎么分布？**
composer 14（解析容错/降级/grounding 注入）、deals_tools 13（过滤/打分/排序/武汉动态计数）、task_planner 12（action 分支/重试/JSON 提取）、safety_guard 11、sqlite_session 10、kb 6（BM25 委托/降级）、deal_catalog_pg 4（回退链 + live PG）、observability 3、streaming 2。

**12.3 离线 e2e 51 项分组？**
S1 主链路（clarify→retrieve→respond 三轮 + 直读 SQLite 断言槽位/轮次交替）；S2 SSE 事件序；S3 杀进程重启同库续聊；S4 护栏拦截 + 会话续用；S5 反馈落库 + 400 语义；S6 观测（7 请求 7 行审计、action 分布、metrics 聚合）。脚本自起自停 api_server、用临时目录的 e2e.db + obs.db，端口被占直接 exit 2。

**12.4 为什么 e2e 要直读 SQLite 断言？**
多轮的核心契约在持久层：turns 的 user/assistant 严格交替、context 槽位的写入与覆盖、跨进程重启的续接。HTTP 响应相同不代表状态写对了——"响应正常但落库错误"只有直读存储能抓。

**12.5 --real 层测什么，为什么允许重试一次？**
7 项语义断言：追问合理性、只补预算不重问城市人数（槽位延续）、"能开发票吗"必须调 kb_search、grounding 非空、轮次持久化。LLM 有采样随机性，单项失败允许重试一次再判 FAIL——既不被随机性刷屏，也不放过真回归。

**12.6 双后端 parity 矩阵怎么设计的？**
同机起 json(:8101) 和 postgres(:8102) 两实例（**矩阵内固定 RETRIEVAL_VECTOR=off**，因为契约是"BM25+过滤下推一致"），20 例覆盖空过滤/组合过滤/max_price=0 边界/people 区间内外/无文本命中兜底/空查询/kb。逐字节 diff：item_id 顺序、除 score 外全字段、total，score 容差 1e-9。无 PG 环境 exit 0 SKIP 不阻塞开发。

**12.7 向量测试怎么证明"向量真的有用"而不只是"没挂"？**
关键是**对比证明**：同一语义 query（"情侣约会"）对 vector=on(:8201) 和 vector=off(:8202) 两实例各发一遍，断言 on 的 top_k 里至少有一条期望类目（西餐/日料/甜品）的商品**不在** off 的 top_k 里——向量通道确实召回了 BM25 漏掉的相关商品。再加类目级语义断言（容忍数据重生成）和两条回归（空查询两实例一致、空过滤集都空）。

**12.8 live PG 测试怎么门控？**
`PG_TEST_DSN` 环境变量：设置则跑"PG 加载 == 文件加载逐字段相等"（5320 条，浮点 EXPECT_NEAR 1e-9 容差吸收 DECIMAL→text→strtod 的 ULP 差），未设置 GTEST_SKIP。默认 CI/离线跑 74 过 + 1 skip，有 PG 的开发机跑全量。

**12.9 CTest 踩过什么坑，怎么修的？**
`gtest_discover_tests` 默认工作目录是构建目录，文件依赖用例（读 data/deals.json）在 RUN_TESTS 下必挂、直接跑 exe 却过——同一份代码两种结果。修：`gtest_discover_tests(test_agent WORKING_DIRECTORY ${CMAKE_SOURCE_DIR})`，两种入口行为一致。

**12.10 数据生成器怎么做到"5000 条且确定性"？**
武汉：20 菜品模板 × 24 地标 × 8 人数档，三个维度用**正交循环长度**（模板每条变 i%20、地标每 20 条变、人数每 480 条变）组合出 3840 个唯一标题，剩余重复一次模拟连锁店；价格/销量/评分/人数区间全是 i 的纯函数。幂等：重跑先删 city=武汉的记录再生成，输出字节稳定。

**12.11 ID 段分配踩过什么坑？**
武汉块 gb-20021..25020 与城市生成器旧段（深圳 20221 起）重叠：第一版城市脚本把 300 条武汉数据当"旧产物"删了。修：城市段迁到 26021/27021/28021，清旧段按 **id 区间 + city 双条件**匹配——id 会撞，id+城市不会。教训：幂等脚本的"删除条件"必须和"生成条件"同样精确。

**12.12 e2e 真实抓出的 4 个缺陷？**
① respond 动作丢失（"谢谢"掉进推荐管道）；② query="包间"无文本命中返回空推荐（改为评分兜底）；③ 纯知识问题不调 kb_search（prompt 规则 4）；④ 推理模型 max_tokens 截断规划 JSON（4096 + 容错 + 温度 0 重试）。共性：都在**组件契约接缝**或**真实模型行为**上，单测盲区，只有端到端能暴露。

**12.13 为什么 e2e 默认要求 CATALOG_BACKEND=json？**
确定性：json 后端从 data/deals.json 读，字节级可复现；postgres 后端依赖本机 PG 状态（是否启动、是否播种），e2e 不能在 CI/离线环境依赖它。PG 路径的正确性由专项测试（live 单测 + parity 矩阵）覆盖，e2e 只锁编排行为。测试分层各管各的契约。

## 十三、工程化与部署（10 问）

**13.1 CMake 怎么集成 libpq 这种可选系统依赖？**
`option(ENABLE_PG_CATALOG ON)` + `PG_ROOT` 缓存变量 → `find_path(libpq-fe.h)` / `find_library(pq)`；找到则 `target_compile_definitions(AGENT_HAVE_LIBPQ=1)` + PUBLIC 链接（传播给 test_agent），找不到只 WARNING 无 PG 编译，源码 `#ifdef` 降级。可选依赖的三要素：编译开关、源码降级、运行时回退，全有。

**13.2 Windows DLL 暂存踩过什么坑？**
两个。① `add_custom_command(TARGET)` 只对**同目录作用域**的 target 有效，根 CMakeLists 里对子目录 target 用会报错——解法是定义 `stage_libpq_dlls(tgt)` 函数由各子目录自己调；② 函数定义在 `add_subdirectory` **之后**时，子目录里 `if(COMMAND ...)` 静默为假，DLL 一个不拷，test_agent.exe exit 127 还不报错——函数定义必须前置。libpq 要拷 6 个 DLL（libpq + libssl/libcrypto + libiconv/libintl/libwinpthread）。

**13.3 pgvector 在 Windows 怎么装上的？**
没有官方 Windows 二进制，源码构建：VS2022 x64 Native Tools 里 `nmake /F Makefile.win`（PGROOT 指 PG17）；install 要写 Program Files 需管理员——本机 sudo 被禁用，走 PowerShell `Start-Process -Verb RunAs` 弹 UAC，且参数必须写成 .ps1/.bat 文件（Git Bash→PowerShell 内联引号会把带空格的路径搞坏）。CREATE EXTENSION 还要 postgres 超管跑，业务账号没权限。

**13.4 Python 依赖纪律是什么？**
pip 依赖按服务圈定、逐个注释用途范围：psycopg + fastembed（仅检索服务）、lightgbm（仅排序服务与训练脚本）、grpcio/grpcio-tools（仅检索服务 gRPC 前端）。网关、e2e、生成器、评估脚本**纯标准库**——保证"clone 下来不装任何东西就能跑离线全链路"。每加一个依赖都要回答"能不能用 stdlib 做"。

**13.5 一键启动怎么做？**
`start_all.bat`：依次起 retrieval_service(:8001)、llm_gateway(:8000)、ranking_service(:8002)、api_server(:8080)，set 好 `RETRIEVAL_SERVICE_URL`、`CATALOG_BACKEND=postgres`、`PG_DSN`。任一进程挂掉对应降级链生效，剩下的还能跑——启动脚本本身也是降级链的演示。

**13.6 凭证怎么管理？**
所有密钥在 gitignored 的 `.env.local`（网关的 LLM_API_KEY、检索服务的 PG_DSN 含密码）；`.env.example` 提交模板；C++ 侧零密钥；gitignore 覆盖两个服务的 .env(.local)。纪律：宁可在启动脚本里写本机开发密码（start_all.bat 是本地工具），也不让凭证进 git。

**13.7 Windows 中文编码有哪些坑？**
三个：① Git Bash 内联 `curl -d '中文'` 经 GBK 泄漏毁字节，必须用 UTF-8 文件 `--data-binary @file.json`；② 控制台 GBK 让 Python 中文 stdout 乱码，脚本里 `sys.stdout.reconfigure(encoding='utf-8')` 或 `python -X utf8`；③ SSE/JSON 序列化用 `error_handler_t::replace` 兜底非法 UTF-8。

**13.8 构建脚本做了什么？**
`build_windows.ps1`：定位 VS 自带 cmake（vswhere 兜底）→ 配置（VS2022 x64）→ Release 构建 → RUN_TESTS。曾暴露 RUN_TESTS 工作目录问题，修完后脚本全绿是提交前门槛。Linux/MSYS2 有对应的 build_phase0.sh。

**13.9 数据变更的标准流程？**
改/跑生成器（确定性幂等）→ `python scripts/pg_seed.py`（单事务 upsert + stale 清理）→ `python scripts/pg_embed.py`（增量补向量）→ 重启 retrieval_service（BM25 语料和向量门控都是启动时构建，不热加载）→ 跑 parity + vector 测试。五步顺序不能乱：seed 在 embed 前，重启在最后。

**13.10 如果让你把这个项目部署上云，第一步做什么？**
不是上 K8s——鉴权（API key）和限流（令牌桶）已在 Phase 5 落地，云上第一步是**打开它们**（AGENT_API_KEYS / RATE_LIMIT_RPS）并把密钥迁到密钥管理；然后会话热数据迁 Redis 让编排层多实例，PG 用托管实例，观测库换正式方案。K8s/服务网格/Prometheus 都在"明确不做"清单里：单机 SQLite + /v1/metrics + evaluate.py 已覆盖当前体量，过度架构比缺架构更致命。

## 十四、学习式排序与 A/B 实验（Phase 2.1，7 问）

**14.1 学习式排序的整体架构？**
第四个进程 `ranking_service`（:8002,LightGBM LambdaRank）。C++ 侧 `RankerClient`（全 virtual，仿 RetrievalClient）注入 `DealRanker`；`model_loaded=false` 是**合法健康态**（冷启动），C++ 回退规则分。模型与特征启动时加载、不热加载——重训后重启服务生效。

**14.2 训练/推理特征怎么保证一致？**
特征组装单点共享 `ranking_service/features.py`——训练（train_ranker.py）和推理（main.py）双端 import 同一份代码；训练产物 meta.json 存 `feature_names`，推理时校验，特征漂移直接报错而不是静默算错。

**14.3 训练数据从哪来？样本不够怎么办？**
`recommendation_logs.candidates_json` 埋点（ranker 输入侧全候选 cap 50，含规则分/模型分）+ feedback 表 like/dislike → `build_features.py` 聚合 item_features → `train_ranker.py` LambdaRank（group=trace_id,label: like=1/dislike=0）。**样本 <100 或正样本 <10 拒绝产模型**——这是刻意的：没有数据就没有模型，链路自动回退规则分，不会产出垃圾模型。

**14.4 A/B 分桶怎么做的？**
`ExperimentManager`：FNV-1a(user_id) % 100 分桶（手写，不用 std::hash 保跨平台确定），空 user_id 恒 control。`RANKER_MODE=off|shadow|active`：shadow 模式规则分服务用户、模型分只进审计做离线对比；active 按 `RANKER_TREATMENT_PCT` 灰度。`rank_mode` 观测三种生效路径：model / rule / rule_fallback。

**14.5 模型服务挂了/返回异常会怎样？**
三层回退：始终先算规则分 → RANKER_MODE=off 或无 client 直接用 → Rank() 失败或 model_loaded=false 回退（rank_mode=rule_fallback）。**taboo 禁忌剔除永远留在 C++ 侧、先于任何模型调用**——模型只能重排幸存者，无法复活被规则剔除的商品。

**14.6 rank_audit 为什么走 tool_result 顶层字段而不是改 ITool 接口？**
观测回传通道原则：组件把审计数据（experiment_group/rank_mode/candidates）放在结果 JSON 的 `rank_audit` 键里回传，orchestrator 识别并写库。ITool 签名零改动，其他工具不受影响——和 Plan.llm_calls 回传是同一模式。

**14.7 排序模型现在上线了吗？**
诚实答案：没有，状态是 ⏸ 数据不足挂起。shadow 灰度已全栈验证（Phase 2.3-C），但真实 feedback 积累未达到训练门槛，`train_ranker.py` 按设计拒绝产模型。解除路径明确：真实会话积累 → build_features → train_ranker → evaluate.py 实验段对比。把"数据不够"做成系统行为而不是口头说明，本身就是设计。

## 十五、用户画像与长期记忆（Phase 2.2，7 问）

**15.1 画像存在哪？**
`user_profiles` 表与会话/反馈同库（sessions.db），但**独立类、独立连接**（SqliteUserProfileStore，WAL+busy_timeout），不污染 SessionMemoryStore 接口。PG 终态 DDL 已备好（sql/003_user_profiles.sql），多实例时迁移。

**15.2 画像怎么算出来的？**
规则式 `PreferenceExtractor`（纯函数、零 LLM）：like 的 item 反查 catalog 聚合 category/city top-3（like +1 / dislike -1）、budget 均值、taboo 去重入 dietary_tags、price_sensitivity = like 中 discount>0.3 的占比。规则式所以确定性、可单测、零成本。

**15.3 画像怎么进 planner？**
`TaskPlanningPrompt` 第 4 参 `user_profile_json`，画像段插在「当前已填充槽位」之前；**空画像时段落完全不出现，prompt 逐字节同前**——行为不变性是测试断言的，不是靠小心。规则明示「当轮显式输入永远优先于画像」。

**15.4 画像多久更新一次？**
请求时惰性计算 + 5 分钟缓存（`updated_at` 字符串比较）：feedback 后不动 handler（写路径零改动），下次请求发现画像过期才重算。惰性计算避免了"反馈后同步重算"的写放大。

**15.5 画像和当轮输入冲突谁赢？**
当轮显式输入永远优先——写在 prompt 规则里。画像只用于预填缺失槽位和排序倾向。比如画像爱吃辣，当轮说"不要辣"，taboo 胜出。

**15.6 画像不可用时会怎样？**
UserProfileStore 不可用/无画像 → planner prompt 无画像段，逐字节同无画像行为。降级链的一环：任何一层挂了，行为退化为该层不存在。

**15.7 前端配合做了什么？**
web/app.js 的 user_id 从硬编码 'web-user' 改为 localStorage 持久 UUID（crypto.randomUUID，兜底手写 UUIDv4，异常回退原值）——画像和 A/B 分桶从此真正分用户，否则所有 web 用户共享一个桶。

## 十六、召回放宽与观测口径（Phase 2.3/3，7 问）

**16.1 空推荐率问题怎么发现的？**
evaluate.py 按三口径拆分后发现：真实流量空推荐率 >20%（sim 模拟数据和 test/stub 流量被剥离开，不污染真实口径）。观测口径先行——不拆口径，模拟数据会把真实问题稀释掉。

**16.2 三级放宽链是什么？**
召回过严导致空推荐时的逐层回退：relaxed_level 0（严格）→ 1（类目放宽）→ 2（价格/人数放宽）。审计经 slots_json 下划线键（`_relaxed_level`/`_effective_category`）回传——additive,消费方只读已知键，不加列。

**16.3 修复效果怎么验证的？**
空推荐率 29.2% → 24.1%，且分子全是修复前的历史日志（docs/phase3_recall_fix.md 有前后对照）。另修了一个语义 bug：max_price=0 从"价格为 0"归一为"不设限"（预算无要求的真实语义），检索服务契约不动。

**16.4 三口径观测是什么？**
evaluate.py 把流量拆成 real（真实用户）/ test（e2e、stub 模型名）/ sim（sim- 前缀的模拟反馈）三个队列，空推荐率、满意率都按口径分开。sim 数据用 `--include-sim` 显式隔离。这是"模拟数据不能污染真实指标"的工程化。

**16.5 流式 compose 的 token 审计怎么做准的？**
网关在流式请求里开 `stream_options.include_usage`，上游尾部 SSE usage chunk 的 tokens 如实落库；上游不给就记 0——**诚实记录原则**：宁可记 0 也不估算冒充。

**16.6 shadow 灰度怎么全栈验证的？**
Phase 2.3-C：RANKER_MODE=shadow 起全栈，规则分服务用户、模型分入审计，逐请求对比两者排序差异；运维 checklist 落盘。验证了灰度链路在无模型时不炸、有模型时双分并存。

**16.7 观测回传通道为什么不直接给组件传 store 指针？**
穿 store 指针会让每个组件都依赖写库细节，单测要 mock 存储。回传式（组件填审计字段、编排器外层壳统一写库）让组件保持纯逻辑，写库只有单一出口，覆盖全部 5 条返回路径。

## 十七、API 鉴权与限流（Phase 5，7 问）

**17.1 鉴权怎么设计的？**
`AGENT_API_KEYS`（逗号分隔多 key）；设置后 /v1/chat、/v1/chat/stream、/v1/feedback、/v1/metrics 要求 `X-Api-Key`，失败 401 带 trace_id；`/v1/health` 与静态资源豁免（健康检查惯例）。**空 = 关闭**，行为与之前逐字节一致——默认不改变任何人。

**17.2 key 比较为什么要恒定时间？**
普通 `==` 在第一个不同字节处返回，响应时间泄漏匹配前缀长度，可逐字节爆破。实现：`diff = (a.size() ^ b.size())` 起手，再扫 max(a,b) 长度逐字节异或，多 key 不提前退出——时间不依赖匹配位置。

**17.3 限流算法和 key 的选择？**
内存令牌桶：`RATE_LIMIT_RPS` 速率 + `RATE_LIMIT_BURST` 容量，refill=min(burst, tokens+elapsed·rps)。限流 key 优先级：user_id → API key → anonymous。空/0 = 不限。

**17.4 SSE 流式怎么计流？**
按请求计 1 次，不按 token——限流防的是请求洪峰，token 数由 LLM 侧 max_tokens 控制。429 响应带 `Retry-After`（据令牌缺口算秒数）和 trace_id。

**17.5 怎么证明默认关闭时不影响存量行为？**
e2e S7/S8 用**独立端口实例**（:8081/:8082）显式开启鉴权/限流验证启用路径；主实例 pin 空值跑原有基线全过——启用与关闭两条路径都有自动化守护。

**17.6 鉴权限流的观测在哪？**
`/v1/metrics` 响应含 `api_guard{auth_rejected, rate_limited}` 计数器——被拒绝的流量也要可观测，否则攻击/误配不可见。

**17.7 单机内存限流多实例怎么办？**
当前是单机演示形态，内存桶够用；多实例时迁 Redis（令牌桶状态共享）或用网关层限流（nginx/envoy）。设计上限流器是独立类，替换存储后端不动调用点。

## 十八、gRPC 双协议试点（Phase 5，7 问）

**18.1 为什么 gRPC 只做试点而不是全量替换 HTTP？**
HTTP JSON 契约已冻结且有完整 tooling（curl 可调试、e2e 直接打）；gRPC 的收益（二进制、强类型、代码生成）需要先在一个边界上验证。选 retrieval_service 试点：调用最频繁、契约最稳定。proto 逐字段镜像 HTTP 形状，**任何 gRPC 失败逐调用回退 HTTP**。

**18.2 双协议怎么并存的？**
retrieval_service 同进程双前端：`GRPC_PORT` 设了就在 HTTP 之外多起一个 gRPC server，两边调同一批 handler 函数；空 = off。C++ 侧 `GrpcRetrievalClient : RetrievalClient`,`RETRIEVAL_PROTOCOL=grpc` 时先走 gRPC、失败 fall through 到基类 HTTP 方法。`ENABLE_GRPC` CMake 默认 OFF——不编译时整个 client 是 HTTP 直通，行为逐字节不变。

**18.3 proto 契约和 HTTP 怎么保证一致？**
两个手段：① presence 语义对齐——`max_price` 等过滤字段在 proto 里用 `optional`（absent=不过滤，0=真 0），Python 侧 `_deals_request_to_body` 保 presence；② `test_pg_retrieval.py` 协议×后端矩阵：grpc≡http 24 例逐字节 diff × postgres/json 双后端。

**18.4 gRPC 失败回退怎么做到运维可见？**
Phase 4 顺带修复（此前是 PM 验收差距）：三处 fall-through 加**限频** spdlog::warn（每 60s 一次，带 op 名和 status code）；channel 建连设 `GRPC_ARG_MAX_RECONNECT_BACKOFF_MS=2000`，服务恢复后在一个请求 deadline 内重连（原默认退避可到分钟级）。

**18.5 工具链踩了哪些坑？（首构 29 分钟）**
四条：① FetchContent providers 全 module 避免系统包混用；② `gRPC_INSTALL=OFF` 不够，`protobuf_INSTALL`/`utf8_range_ENABLE_INSTALL` 必须一起关，否则导出集报错；③ `grpc::ClientContext` 不可拷贝，MakeContext 返回 unique_ptr；④ GitHub 直连超时，手工 clone + `FETCHCONTENT_SOURCE_DIR_GRPC` 免下载，镜像 rewrite 限 repo-local/命令级（用户授权），SHA 与上游校验一致。

**18.6 Python 侧的 pb2 代码怎么管理？**
`retrieval_service/gen/` 提交入库（`scripts/gen_grpc_py.py` 可再生成），grpcio/grpcio-tools 仅检索服务需要——守住"其余脚本纯 stdlib"纪律。

**18.7 怎么证明流量真的走了 gRPC 而不是悄悄回了 HTTP？**
PM 验收的实证方法：gRPC 端口在线时，HTTP 访问日志**零增长**证明没走 HTTP；把 gRPC 端口宕掉，观察到回退 HTTP 且业务不断。限频 warn 落地后这个证据还会出现在日志里。

## 十九、输出事实校验 Guard（Phase 4，7 问）

**19.1 为什么有了 prompt 软约束还要输出事实校验？**
「价格必须来自数据库」是交易红线，prompt 里写"禁止编造"只是软约束，LLM 仍有概率幻觉。输出 FactCheck 是**机制级**防控：回复发出前，规则式核验每个货币断言，违规的回复根本不到达用户。规划文档 1.1「合规与兜底」的输出侧空缺就此闭环。

**19.2 校验规则具体是什么？**
从回复抽取 ¥xx / xx元 / xx折 三类断言，与候选商品 {price, original_price} 精确比对；**派生白名单**防误杀：人均（price/人数 floor/ceil ±0.51）与总价（price×人数）合法，人数取商品自身 [min_people,max_people] 区间（cap 1..20）；折扣按 price/original×10 ±0.5 容差。规则式、零 LLM 调用、回复 <2KB 扫描 <<1ms。

**19.3 误杀怎么防？**
三道：派生白名单（诚实表述"人均 96 元""四人共 1152 元"不被杀）；容差设计（取整双向、折扣半折）；e2e 80 项 + 真模型 7 项全过即"零误杀"实证——stub 模板与真模型回复都没触发误拦截，误杀案例会进 e2e 防回归。

**19.4 非流式和流式违规处理有什么不同？**
非流式：回复还没发出，直接换模板兜底（compose_mode=template_guard_fallback）。流式：token 已经逐段发给用户了，无法回收，所以全文校验在流完成后做，违规时尾部发 additive 的 `replace` SSE 事件（模板兜底内容）整体纠偏；旧前端不认识 replace 走 default 忽略不崩。流式体验不破，违规才介入。

**19.5 Guard 动作怎么观测？**
`recommendation_logs` 幂等加列 `guard_action`（refuse_input/sanitized/fact_violation）+ `guard_detail`（违规摘要 cap 400)，经观测回传通道写库；evaluate.py「Guard 动作」段出分布、fact_violation 率（>5% 告警）、最近 10 条明细。审计先行：所有介入可复算。

**19.6 规则为什么要外置？**
违禁词/注入模式/违禁话题/长度阈值在 `data/guard_rules.json`，改规则不改代码。缺文件/损坏回退内置默认（与内置逐字节一致，PM 移走文件实测注入仍被拦）——降级链哲学延伸到配置层。

**19.7 这套 Guard 的边界在哪？**
只管事实断言（价格/折扣）与违禁内容，不管"推荐得好不好"；LLM 级深度审查（语义幻觉、偏见）评估为演示项目非必需，封存在 roadmap。诚实边界比宣称"全覆盖"更重要。

## 二十、数据真实性工程（Phase 7，7 问）

**20.1 为什么选「真实 POI + 合成 deal」而不是直接爬团购网站？**
合规与成本双重考量：团购平台的商品价格/销量是动态商业数据，爬取涉反爬对抗（滑块/封 IP/登录墙）且有法律风险；高德开放平台 Web 服务 API 是**官方授权通道**（个人开发者免费额度），拿到的是静态事实数据（商户名/地址/坐标/评分）。团购属性（价格/折扣）本来就是我系统的合成演示数据，真实性增益全在「商户真实存在」上。面试时必须主动说清这条边界：**商户是真实的，deal 是合成的**。

**20.2 高德 around 接口单中心只返回 200 条，怎么拉到 5000+？**
网格化：把南山区外包矩形（113.88~114.07, 22.48~22.62）切成 2km 步长的 99 个中心点，每个中心做半径 1.3km 的圆搜索（step ≤ √2·radius 保证覆盖），重叠部分按 poi_id 去重。around 接口第 9 页起返回空（无论 count 报多少）是实测出来的上限，不是文档写的——所以网格密度按「单圆内真实 POI 数 < 200」来设计。495 次请求拉到 5408 个去重 POI。

**20.3 配额有限怎么保护？**
三层：① 每页原始响应落盘缓存（仅缓存 status=="1" 的成功页，失败页不缓存防污染），重跑零网络请求；② 请求间隔 1s 限速；③ `_quota.json` 当日计数 + `AMAP_DAILY_LIMIT` 熔断（默认 4000），触顶保留已缓存部分次日续跑。缓存 key 含中心坐标，网格中心互不冲突。

**20.4 类目怎么对齐？高德 typecode 和你的 22 类目完全不同。**
显式映射表（typecode 叶子名 → catalog 类目，33 条规则），**未映射的跳过并逐类计数报告，绝不硬塞**。5576 个 POI 映射 4394（78.8%），跳过 1182 里 1021 是「餐饮相关」泛类（无类目信息，诚实跳过）。误映射比少数据更伤害演示可信度—— reviewer 一眼能看出"奶茶店被标成火锅"。

**20.5 确定性幂等怎么保证？**
两个坑都踩过：① Python 内置 `hash()` 对 str 是进程随机的，必须 `md5(poi_id)` 做变异源；② 生成器按 id 区间自清除再生成（gb-4xxxx 段与既有 2xxxx/26-28xxx 无冲突），连跑两次输出逐字节一致（实证）。district 归一去「区」后缀（南山区→南山）匹配 catalog 惯例，否则区过滤器全空。

**20.6 数据规模翻倍（5320→9713）动了哪些地方？**
生成器 → pg_seed（9713 synced）→ pg_embed（4214 新向量）→ 重启检索服务（BM25 语料启动时构建不热加载）→ `test_deal_catalog_pg.cpp` 硬编码计数同步（CLAUDE.md 明示的唯一硬编码点）→ 双后端矩阵 24+24、e2e 80 项、PG live 逐字段比对全绿。测试计数动态推导的设计（test_deals_tools）在这里兑现：只有一处硬编码要改。

**20.7 接真实数据后发现了什么合成数据时代看不到的问题？**
两个：① 合成数据的价格带是均匀设计的，真实商户用类目基准价合成后，「人均 100」预算会过滤掉全部火锅（base 228），空推荐率暴露价格带失真；② 演示冒烟时 LLM 网关没起，传输失败走 FALLBACK 而非内置 stub（stub 仅在 LLM_BASE_URL 为空时启用）——降级链的真实行为只有全栈实测才暴露。
