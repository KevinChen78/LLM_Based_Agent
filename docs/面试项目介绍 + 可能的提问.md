# 一、面试项目介绍（2 分钟版）

> 配套题库：[面试题库_全模块.md](面试题库_全模块.md)——13 个模块 × 每个 ≥10 问（共 158 问），按模块逐个击破。

> 各位面试官好，我介绍一个我最近独立完成的 LLM 应用项目：**基于 LLM 多轮会话的智能团购推荐 Agent**。
>
> 这个项目的定位是：让用户用一句自然语言，比如"上海三个人吃海鲜预算三百"，完成从理解、追问、召回、排序到生成推荐理由的完整推荐闭环。我把它做成了一套 **C++20 协程控制面 + Python 数据面的微服务架构**：C++ 侧基于自研 coro 协程库承载高并发的 Agent 编排，包括显式状态机、任务规划器、工具路由和 SSE 流式推送；Python 侧是 LLM Gateway 和 BM25 检索服务两个独立微服务。
>
> 工程上有三个我认为最有价值的点。**第一是幻觉防控**：LLM 只负责理解和表达，价格、销量等事实字段全部由商品库强制回填，事实类问题走知识库检索并附"回答依据"，从机制上而不是提示词上杜绝编造。**第二是稳定性治理**：接入 DeepSeek 推理模型后，我发现约三分之一的请求因为推理 token 挤占输出导致规划 JSON 被截断，通过"容错 JSON 提取 + 温度 0 重试 + token 配额调优"三级容错，把规划成功率提升到 15/15。**第三是质量体系**：我建立了 71 个单元测试加双层端到端回归——离线确定性层 51 项断言可以秒级复跑，真实 LLM 层验证语义级槽位延续；这套回归在开发过程中真实抓出了 4 个行为缺陷。
>
> 此外系统还具备 Token 级流式回复、SQLite 会话持久化、反馈落库和每请求审计观测能力，配有一键启动脚本和 Web 对话界面，是一个可以现场演示的完整闭环产品。

# 二、面试问答（按主题分类）

## A. 架构设计

**Q1：为什么控制面用 C++、数据面用 Python，而不是全 Python？** 控制面是 Agent 编排和 API 接入，特点是高并发、大量 IO 等待（等 LLM、等检索），C++ 协程能用极低的资源开销撑起高并发连接，这也是我的技术栈优势所在。而 LLM 调用聚合、检索排序这类"数据重、迭代快"的逻辑用 Python，开发和算法迭代效率高。这是修订版规划里明确的"控制面/数据面分离"原则，也避免在 C++ 里硬写推荐模型。

**Q2：为什么基于自研 coro 协程库，而不是直接用成熟框架？** 项目规划时就确定复用团队已有的 coro 库（`coro::Task<T>` + ThreadPool + HTTP Server）。实际开发中我也深入到了框架层——比如 SSE 流式需要 chunked 传输支持、路由是精确键匹配不支持多段通配，这些约束直接影响了前端静态资源的路由设计（扁平目录 + 显式路由），说明我不是"调库"，而是理解框架边界并在边界内设计。

**Q3：为什么用 SQLite 而不是 Redis/PostgreSQL？** 当前是单机可演示形态，SQLite WAL 模式支持一写多读、零部署成本，会话、反馈、审计三个库完全够用。schema 设计时有意对齐了修订版规划里的 PostgreSQL DDL（表名、字段、索引一一对应），迁移时只需换连接层。这是"按当前规模选型、按目标形态设计"。

**Q4：三个数据文件（sessions.db / feedback 在 sessions 库 / observability.db）为什么这么拆？** feedback 有外键指向 sessions，必须在同库；观测审计没有外键需求且写入频率高，独立成 observability.db 避免与会话读写竞争，也让审计数据可以独立备份和保留。反馈满意率需要跨库 join 时，用 SQLite 的 ATTACH 解决。

**Q5：如果 QPS 上来、要多实例部署，架构怎么演进？** 编排层本身是无状态的（会话状态全在存储层），可以直接水平扩展；瓶颈在存储：会话记忆迁 Redis（短期 TTL）+ PostgreSQL（持久化），检索服务 BM25 换 Elasticsearch/pgvector。这个演进路径在 README 的 Phase 2 路线图里有明确规划。

## B. LLM Agent 设计

**Q6：Agent 状态机是怎么设计的？** 显式六态：INIT→SLOT_FILL（槽位补全/追问）→RETRIEVE（召回）→RANK（排序）→EXPLAIN（生成理由）→RESPOND（回复），任何一步失败可进 FALLBACK 兜底。状态流转由 TaskPlanner 解析 LLM 的结构化 JSON 输出决定——LLM 输出 action（clarify/retrieve/respond）、槽位、缺失槽位和工具调用计划，编排器据此执行。

**Q7：为什么"LLM 只做理解和表达，不碰数据"？** 团购是交易场景，价格、库存错了就是纠纷。所以硬过滤（城市/价格区间/有效期）不经过 LLM，召回排序由检索和规则系统完成，推荐理由由 LLM 生成但价格字段从商品库回填。LLM 的输出永远被结构化校验，这是合规底线。

**Q8：DeepSeek 推理模型截断问题具体是怎么回事，怎么解决的？** e2e 时发现约 1/3 请求 FALLBACK。排查发现推理模型先输出大量 reasoning token，max_tokens=1024 时规划 JSON 在 `"tool_name` 键名处被截断。三级修复：max_tokens 提到 4096；实现容错 JSON 提取器（干净 JSON → ```json 围栏 → 首尾花括号截取，三档递进）；解析失败时温度 0 确定性重试一次再兜底。修复后 15/15 成功，并有 5 个针对性单测防回归。

**Q9：多轮对话的槽位延续怎么实现？** 会话历史（最近 10 轮）和已填槽位都注入 planner prompt，由 LLM 结合上下文重新吐出合并后的槽位集合。这里有个被 e2e 抓出来的坑：context 是整体覆盖的，respond 类型的轮次会把槽位清空——这是设计内行为但要求 planner 每轮都从历史里重建槽位。真实 LLM 层的回归专门验证了"第一轮说上海 3 人，第二轮只说预算 300，不会再被追问城市和人数"。

**Q10：回归中发现的 4 个缺陷，挑一个讲？** 最有代表性的是 respond 动作丢失：用户对推荐说"谢谢"，planner 正确输出了 `action:"respond"` 和应答文本，但编排器没有处理这个分支，直接掉进了推荐管道，空商品触发了"暂时没有符合条件的团购"——用户体验完全错误。修复是在编排器加 respond 短路路径。这个 bug 单测测不出来，因为它在 planner 和编排器的**契约接缝**上，只有端到端多轮回归能暴露。

**Q11：纯知识问题（比如"能开发票吗"）怎么走通链路的？** planner prompt 规则明确：纯事实问题同样走 retrieve action，但 tool_calls 只放 kb_search，不受槽位缺失限制；检索知识库后 passages 注入 composer 的"# 参考知识"段，空商品但有 grounding 时不走"没有团购"的短路文案，而是让 LLM 基于知识作答。这个行为也是 e2e 抓出来后修好的——原来 prompt 只在"推荐商品"语境下提 kb_search，模型对纯问题直接 respond 跳过了检索。

## C. 检索与 RAG

**Q12：为什么自研 BM25 而不是直接用向量检索？** 项目起步时商品量仅数百条，BM25 在千级以内效果和延迟都足够好，且零依赖、纯标准库实现、确定性强、可解释。数据扩到 5000+ 后引入了 pgvector 向量召回，但不是替换而是 **BM25 + 向量 RRF 融合**（k=60）：BM25 保精确匹配与可解释性，向量通道（fastembed bge-small-zh-v1.5，512 维，HNSW 余弦 ANN）补同义词/口语查询的语义泛化，两路候选按倒数排名融合，任一通道缺失自动降级。选型原则是匹配当前规模、渐进演进。

**Q13：中文分词怎么做的？** CJK 字符二元组（bigram）切分——对中文检索来说，bigram 在无词典依赖的前提下兼顾了精度和召回，比如"小龙虾"切成"小龙/龙虾"。英文按词干小写切分。参数用经典 k1=1.5、b=0.75。

**Q14：BM25 召回为空怎么办？** 两级兜底：文本无命中时，在结构化过滤后的候选集里按评分降序返回，而不是返回空——这是 e2e 发现的坑（query="包间"无文本匹配导致空推荐）；整个检索服务不可达时，C++ 侧降级为本地子串匹配，链路不断。

**Q15：RAG 的 grounding 怎么注入生成的？** kb_search 返回 passages，编排器格式化为"【标题】内容（来源：xx）"，composer 构造 prompt 时注入"# 参考知识（回答问题时以此为准，不要编造）"段，流式和非流式两条路径都注入。前端把 grounding 渲染为可折叠的"回答依据"面板。

## D. 流式与前端

**Q16：SSE 流式是怎么实现的，有什么技术难点？** 三个难点：一是 httplib 的 POST 不支持 ContentReceiver，所以 LLM 流式调用用裸 socket 手写 HTTP 请求并逐行解析 SSE，还要处理 localhost 的 IPv4/IPv6 双解析遍历；二是网关在 C++ 和上游之间做 SSE 字节级透传；三是浏览器 EventSource 只支持 GET，而我的端点是 POST，前端改用 fetch + ReadableStream 手动按 `\n\n` 切块解析事件。

**Q17：SSE 事件流设计了哪些事件？** started（带 session_id）→ input_guard → planning → plan（带缺失槽位）→ tool_call/tool_result 成对 → grounding → composing → delta（逐 token）→ final（完整 12 字段商品卡片 + grounding）/ error。前端据此渲染"思考过程"折叠面板、打字机效果和商品卡片。final 的 items 曾经只有 8 个字段，为了卡片展示补齐到 12 个。

## E. 质量与测试

**Q18：测试体系怎么设计的？** 三层：71 个 gtest 单测覆盖各组件契约；e2e 回归分两层——离线确定性层用 C++ 内置 stub（三分支确定性规划），51 项断言覆盖多轮主链路、反馈落库、SSE 序列、重启持久化、安全护栏、观测审计，秒级可重复；真实 LLM 层验证 stub 测不了的语义行为（槽位延续、kb grounding），允许重试一次对抗模型随机性。脚本自动起停服务、用临时数据库、直读 SQLite 验证持久层。

**Q19：为什么 e2e 要直读 SQLite 断言，而不是只测 HTTP 响应？** 因为多轮的核心契约在持久层：turns 表的 user/assistant 交替、context 槽位的写入与覆盖、跨进程重启后的会话续接。HTTP 响应相同不代表状态写对了。直读存储让回归能抓到"响应正常但落库错误"这类隐蔽问题。

## F. 观测与反馈

**Q20：观测体系怎么做的？** 每次请求一行 recommendation_logs（action/槽位/Top5 商品/compose_mode/端到端延迟），每次 LLM 调用一行 llm_calls（用途/模型/token/延迟/重试序号），trace_id 串联。实现上用了"回传式"设计：Plan 和 compose 结果把 LLM 调用元数据带回编排器统一写库，planner/composer 签名零改动；编排器拆外层壳（计时+写库，单一出口覆盖全部 5 条返回路径）和内层（原逻辑不动）。聚合走 `/v1/metrics`，离线评估用 `evaluate.py`。

**Q21：反馈闭环怎么设计的，数据有什么用？** 每条回复和每张商品卡片有 👍/👎，落 feedback 表（含 trace_id 和 item_id，外键关联会话），目前被 metrics 的满意率和评估报告消费；它是 Phase 2 学习式排序的训练信号——item 级反馈可以做 CTR/CVR 特征，答复级反馈衡量整体推荐质量。

## G. 开放追问（压力题）

**Q22：这个项目最大的不足是什么？** 三个诚实答案：一是召回还是 BM25 规则排序，没有学习式排序模型（数据基础刚打好）；二是单机部署形态，没有鉴权限流，还不是生产服务；三是延迟依赖单一上游模型，p95 约 7 秒（推理模型），需要多模型 fallback 和更快的模型分层。这些都在 Phase 2 路线图里，我也知道先做什么：特征存储 + LightGBM 排序服务 + 影子模式对比。

**Q23：如果商品量到 100 万，你要改哪里？** 四处：商品库迁 PostgreSQL（DDL 已设计好）；BM25 换 ES + 向量多路召回；排序换模型服务（C++ 侧只留 RankerClient）；会话热数据迁 Redis。编排层和 LLM 层基本不动——这正是当初控制面/数据面分离的意义。

**Q24：LLM 成本怎么控制？** 已做的：planner 只在解析失败时重试一次、compose 有模板兜底不盲目调 LLM、审计表按用途统计 token 消耗（plan/compose 分开归因）。可以做的：简单意图用小模型分层（`LlmModelTier` 已预留）、高频相似请求的规划结果缓存、Prompt 中商品数上限截断（已限 10 条）。

**Q25：安全性怎么保障？** 输入护栏在规划前拦截 prompt 注入（中英文越狱话术）、违禁话题和超长输入，命中短路拒答；输出侧脱敏手机号/邮箱/身份证，过滤违禁词；反馈和会话接口都有参数校验和外键约束；静态文件服务有路径穿越防护。全部规则式、零额外 LLM 调用，确定性可测。
